## Abstract

Structural Folding converts populations of concrete experience into reusable structural memory. Structural Unfolding uses that memory to construct candidate structures for new goals.

CallingGraph-based AI coding provides a canonical domain in which these two processes can be connected into a complete lifecycle.

A mature or certified software program can be transformed into a CallingGraph. A population of mature programs therefore produces a population of CallingGraphs. These CallingGraphs can be represented through **GenericContainerStarmaps**, structurally compared, Folded into Metric Differential structures, summarized through Cluster-Central CCCs, decomposed into Core–Delta patterns, and encoded through reusable CallingGraph DNA such as role-normalized Bigram and Trigram relations.

The resulting folded CallingGraph memory can then support a new software requirement.

Instead of generating a program from an undifferentiated state, the system can:

> **Localize → Search Certified Structural Memory → Retrieve Core / Delta / DNA → Unfold a Candidate CallingGraph → Search for Counter-Evidence → Validate → Execute → Certify → Refold**

This creates a closed structural intelligence loop:

> **Fold → Search → Unfold → Validate → Certify → Refold**

The key insight is:

> **A CallingGraph can be an Unfolding product at one stage and a Folding individual at the next stage.**

CallingGraph intelligence therefore provides a concrete bridge from Structural Folding to Structural Generation.

A CallingGraph captures program structure through relationships among:

* entry points,
* functions,
* methods,
* modules,
* services,
* persistence layers,
* validation layers,
* control paths,
* failure paths,
* and other runtime or design-time dependencies.

It therefore contains something fundamentally different from raw source text.

It contains:

> **explicit reusable structural organization**

This makes CallingGraph a natural object for Structural Intelligence.

# 4. From One CallingGraph to a CallingGraph Population

A single CallingGraph is useful for:

* understanding one program,
* validating one runtime,
* visualizing one execution structure,
* or generating one design.

But Structural Folding becomes much more powerful when many mature CallingGraphs are available.

Suppose:

$$
CG_1, CG_2, \ldots, CG_N
$$

represent certified programs.

Then:

$$
\mathcal{CG}
=
\{CG_1,CG_2,\ldots,CG_N\}
$$

becomes a structural population.

This is the first major shift:

> **CallingGraph intelligence should evolve from one-graph reasoning toward population-level structural learning.**

# 9. CallingGraph Bigram Representation

Consider a CallingGraph path:

```text id="cg08"
A → B → C → D → E
```

Its Bigrams are:

```text id="cg09"
A → B
B → C
C → D
D → E
```

These Bigrams provide simple local structural relations.

They can be:

* counted,
* compared,
* indexed,
* searched,
* folded,
* and associated with outcomes.

---

# 10. CallingGraph Trigram Representation

The same path produces Trigrams:

```text id="cg10"
A → B → C
B → C → D
C → D → E
```

Trigrams preserve more local context than Bigrams.

They can distinguish structures that share edges but differ in local sequencing.

Thus:

```text id="cg11"
Bigram
  ↓
Cheap Local Relation

Trigram
  ↓
Richer Local Context
```

Both can become structural DNA elements.

---

# 11. SOS Linkage Encoding

Bigram and Trigram representations provide a useful way to encode **sequence-of-structure linkage**.

They allow the CallingGraph to be decomposed into reusable local relations without requiring every comparison to perform expensive whole-graph matching.

A canonical escalation is:

```text id="cg12"
Node / Role Similarity
      ↓
Bigram Similarity
      ↓
Trigram Similarity
      ↓
Path Similarity
      ↓
Whole-Graph Similarity
```

This follows the GFSFUI Compute-by-Need principle.

# 13. Local UTN Before Universal UTN

CallingGraph Folding faces a bootstrapping problem.

Cross-program Folding requires comparable identities.

But a complete Universal Typing/Naming system may itself require large-scale structural comparison.

The solution is:

> **Localize UTN first. Universalize progressively.**

A practical path is:

```text id="cg16"
Raw Program Symbol
       ↓
Local Identity
       ↓
Local UTN
       ↓
Structural Role
       ↓
Candidate Cross-Program Equivalence
```

This is sufficient to begin Folding.

---

# 14. Minimum Sufficient CallingGraph UTN

The initial identity layer needs to be:

1. **Comparable**
2. **Context-Preserving**
3. **Traceable**
4. **Promotable**

It does not need to solve universal software ontology in advance.

This avoids turning UTN into a prerequisite that blocks CG Folding.

# 22. CallingGraph DNA

Recurring local relations may become:

> **CallingGraph DNA**

Examples:

```text id="cg24"
VALIDATE → AUTHORIZE
AUTHORIZE → SERVICE
SERVICE → PERSIST
PERSIST → AUDIT
```

or Trigram DNA:

```text id="cg25"
VALIDATE → AUTHORIZE → SERVICE
AUTHORIZE → SERVICE → PERSIST
SERVICE → PERSIST → AUDIT
```

DNA can represent reusable local structure independent of one entire CallingGraph.

---

# 23. CallingGraph DNA Can Be Contextual

The same DNA may have different meanings under different contexts.

For example:

```text id="cg26"
SERVICE → CACHE → PERSIST
```

may be useful in one workload but harmful in another.

Therefore CallingGraph DNA should preserve:

* context,
* outcome,
* certification,
* and provenance.

DNA without context can become misleading.

# 24. Two-Way CallingGraph CCC

Suppose a CG DNA \(D\) is associated with successful outcome \(Y\).

The system can ask:

$$
D \rightarrow Y?
$$

and:

$$
Y \rightarrow D?
$$

This helps answer:

* Does this structural pattern tend to appear in successful systems?
* Do successful systems usually require this pattern?
* Are there strong alternatives?
* Does the pattern also appear in failed systems?

Two-Way analysis makes the structural memory richer.

# 31. Structural Unfolding

CallingGraph Unfolding transforms reusable folded structure into a new context-specific candidate.

Conceptually:

$$
(\mathcal{M}_{CG},R,C)
\rightarrow
CG_{candidate}
$$

where:

* \(\mathcal{M}_{CG}\) is CG structural memory,
* \(R\) is the new requirement,
* \(C\) is the target context.

The process may reuse:

* Core,
* Delta,
* DNA,
* path fragments,
* role patterns,
* certified alternatives,
* local specialists,
* and known constraints.

---

# 32. Unfolding Is Not Copying

CallingGraph Unfolding should not simply copy an old program.

The new context may require:

* different local names,
* different framework APIs,
* different persistence technology,
* different security constraints,
* different performance tradeoffs,
* different deployment architecture,
* or new Delta.

Therefore:

> **Unfolding reuses structure while adapting context.**

> **CallingGraph Structural Falsification**

# 37. CallingGraph Counter-Evidence Questions

Useful questions include:

1. Where has this path succeeded?
2. Where has the same path failed?
3. Where does the same prefix lead somewhere else?
4. Which mature programs insert an additional node?
5. Which mature programs omit one proposed node?
6. Which certified programs use an alternative topology?
7. Which rejected programs contain this same DNA?
8. Under which contexts does this structure become unsafe or inefficient?

These questions turn historical software into active structural evidence.

# 38. CallingGraph Counter-Evidence Matrix

| Candidate DNA | Successful Outcome | Failed / Rejected Outcome |

| DNA-X present | Supporting CGs     | **Counter-Evidence CGs**  |
| DNA-X absent  | Alternative CGs    | Background / Other        |

The failure cell is highly informative.

It may expose a missing condition or structural Delta.
